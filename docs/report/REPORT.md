## 1. Problem and users

Freelancers on marketplaces such as Upwork spend hours reading job posts, deciding which ones are worth the Connects (paid bid credits), and writing proposals. Generic proposals get few replies, scam posts try to move people off the platform, and posts sometimes contain hidden instructions aimed at AI tools. GigBid is a copilot for one freelancer at a time: it reads jobs, decides bid / skip / watch, writes a proposal grounded in the freelancer's own portfolio evidence, handles client messages, and **never sends anything without a human approval** (a LangGraph `interrupt()` before every proposal, message and Connects spend).

Users: three synthetic personas (AI/ML engineer, full-stack developer, data analyst), each with a profile, CV, portfolio projects, past proposals and client reviews.

## 2. System architecture

- **GigSim** (`gigsim/`): a FastAPI marketplace simulator with its own Postgres schema, a simulated clock, rate limiting, chaos errors (including "lost response"), idempotency keys and client-reply behaviour. It is frozen (`gigsim/FROZEN.sha256`) so evaluations stay comparable.
- **Three MCP servers** (`mcp_servers/`, official MCP Python SDK, Streamable HTTP, bearer auth): *Portfolio* (evidence search, case studies, profile, claim verification), *Marketplace* (jobs, client history, market rates, Connects, proposal draft/submit) and *Workspace* (messages, calendar slots, tentative holds). Every write tool takes `idempotency_key` and `dry_run`; every call is audited with PII masking. Tool schemas are snapshotted and contract-tested (`tests/contract/`).
- **Agents** (`agent/`): two hand-written LangGraph `StateGraph`s.
  - *Bid graph*: `scout_in` -> parallel fan-out (`Send`) to **Job Analyst || Risk Assessor || Fit Matcher** -> `decide` (bid / skip / watch) -> `pricing` -> `writer` -> `verify_claims` -> `critic` (loop back to the writer, at most 2 rounds) -> `compliance` -> `prepare_approval` -> **`approval` interrupt** -> `submit` (or `apply_edit` -> compliance re-check, or reject) -> `record_outcome`.
  - *Conversation graph*: `new_message` -> `classify_intent` -> `propose_slots` / `draft_reply` -> `message_compliance` -> **`message_approval` interrupt** -> `send` -> `update_pipeline`.
  - Agents reach data only through MCP tools on a per-agent allowlist (`agent/config.yaml`). Every hand-off is a Pydantic model (`agent/handoffs.py`). Prompts live only in `agent/prompts/<node>.v1.md`; thresholds, budgets and rules only in `agent/config.yaml` and `data/policy_pack/`.
- **API** (`apps/api/`): FastAPI with multi-user auth (scrypt password hashes, JWT session cookie), tenant id on every query, an SSE bridge from LangGraph `astream`, approval endpoints that resume interrupted threads (pending approvals are read from the checkpointer, so a refresh never loses them) and a Fernet-encrypted OAuth token store.
- **Web** (`apps/web/`): Next.js + TypeScript using only the client generated from the OpenAPI schema. Screens: onboarding, inbox, job, studio (evidence on hover for every claim, approval panel with edit diff, dry-run preview and Connects cost), pipeline kanban, messages, run timeline (live over SSE), analytics and settings (autonomy, budgets, saved searches, accounts, memory viewer with delete).
- **Storage**: Postgres 16 + pgvector (vectors, checkpoints, long-term memory), Redis, Arize Phoenix for tracing; everything starts with `docker compose`.

**Exactly-once submission.** The submit step uses idempotency keys `<thread>:submit:v<draft version>`. If the response is lost, or the process dies inside `submit`, the checkpoint still says `submit` has not completed; on resume the call is repeated with the same key and the marketplace replays the original result instead of charging Connects twice. This is covered by tests (`tests/unit/test_graphs.py`: lost response, crash-then-resume; `tests/unit/test_api.py`: a second approval returns 409 and does not submit).

## 3. Data

Public Kaggle job-post datasets (licences recorded in `docs/DATA_CARD.md`) seed realistic titles, skills and budgets; deterministic generators (seed 20261115) build clients, personas, portfolios and a dev set of 600 jobs (200 per persona) whose gold labels come from construction: job type (bid, scam, missing skill, low budget, ...), planted prompt injections, and the evidence items a good proposal should cite. A held-out test set is generated the same way and is kept out of the repository.

## 4. Retrieval (R&D B)

Hypotheses were written before running (`evals/HYPOTHESES.md`). Six variants run behind one interface (`rag/variants/`): V0 naive dense, V1 query decomposition, V2 hybrid BM25 + dense with reciprocal-rank fusion, V3 V2 + cross-encoder reranking, V4 V3 + outcome boost (evidence from won jobs), V8 corrective RAG as a LangGraph loop that can refuse when evidence is weak.

Source: `evals/results/rag/dev/*.json` (all three personas, dev set).

| Variant | Recall@5 | Project recall@5 | MRR | nDCG@10 | Correct refusal | p95 ms |
|---|---|---|---|---|---|---|
| V0 naive | 0.204 | 0.483 | 0.394 | 0.295 | 0.000 | 394 |
| V1 decompose | 0.189 | 0.429 | 0.331 | 0.246 | 0.000 | 502 |
| V2 hybrid | 0.216 | 0.482 | 0.402 | 0.297 | 0.000 | 19 |
| V3 rerank | 0.193 | 0.444 | 0.337 | 0.278 | 0.000 | 10896 |
| V4 outcome | 0.199 | 0.456 | 0.325 | 0.273 | 0.000 | 13 |
| V8 corrective | 0.174 | 0.397 | 0.291 | 0.249 | 0.874 | 25845 |

Findings:

- **V2 hybrid is the best and cheapest pipeline** (highest Recall@5, MRR and nDCG@10, p95 19 ms). It is the production retriever and the base of the ablation.
- **Reranking did not help on this corpus** and cost about 11 s p95 on CPU. The reranker prefers long proposal texts, so client reviews (a large share of the gold evidence) are pushed out of the top 5. It helps only on jobs that name every skill explicitly (Recall@5 0.230 vs 0.207 for V2 on that slice).
- **V8 corrective RAG refuses correctly on 87.4% of no-evidence jobs** but also refuses on 9.7% of jobs that do have gold evidence, and is the slowest variant. Our hypothesis that corrective retrieval would improve recall was refuted; its value is the refusal behaviour, which protects against unsupported claims.

Ablation (one component off at a time from the V2 pipeline: per-requirement queries + BM25 + dense + structured chunks; source `rag/dev/ablation.json`):

| Removed component | Recall@5 | Project recall@5 | MRR | nDCG@10 |
|---|---|---|---|---|
| none (base) | 0.216 | 0.482 | 0.402 | 0.297 |
| per-requirement decomposition | 0.282 | 0.629 | 0.488 | 0.374 |
| BM25 channel | 0.189 | 0.429 | 0.331 | 0.246 |
| structured chunking | 0.230 | 0.513 | 0.409 | 0.305 |

The most useful result of the study: **removing per-requirement decomposition gave the best configuration we measured** (Recall@5 +0.066, MRR +0.086 over V2). Splitting a job into one query per requirement fragments the context that makes a portfolio item relevant, which also explains why V1 is below V0. The BM25 channel matters (removing it costs -0.071 MRR); structured chunking makes little difference. Switching the production retriever to the whole-job hybrid query is the next change.

**Better retrieval did not always raise reply rate.** On a fixed set of 30 bid-worthy jobs per persona with a deterministic template writer (source `gigsim/outcomes.json`), every grounded variant beat a generic letter (reply rate 0.111), but differences between variants were small: V2 and V4 0.422, V0 and V3 0.389, V8 0.367. V3 had better must-have coverage (0.64) than V2 (0.61) without a higher reply rate, because the simulated client weighs relevance of the top evidence and price, not coverage alone.

## 5. Claim verification

Each sentence of a draft that states a fact about the freelancer is checked against retrieved evidence by a judge (cross-encoder with strict number matching); unsupported claims are repaired or removed before the human sees the draft. ## 6. Multi-agent orchestration and decisions

The bid graph's decisions are evaluated on all 600 dev jobs in deterministic rules mode against a keyword baseline. Source: `decision/graph.json`, `decision/keyword.json`.

| Decider | bid/skip macro-F1 | Accuracy | Scam precision | Scam recall | Price in band |
|---|---|---|---|---|---|
| Graph (parallel analysts) | 0.870 | 0.870 | 0.905 | 1.000 | 0.608 |
| Keyword baseline | 0.696 | 0.717 | 0.905 | 1.000 | 0.652 |

The graph improves bid/skip macro-F1 by 0.174 because the Risk Assessor uses client history (rating, hire rate, unverified "ghost" clients) and the Fit Matcher weighs must-have skills, which keywords cannot see. Both catch every scam. The keyword baseline prices slightly better, a known weakness of the graph's pricing node. Skip-reason accuracy for the graph is 0.817.

**R&D C: is multi-agent worth it?** We ran three systems on the same 50 dev jobs (seeded and stratified by persona), all with the same local model (`ollama:llama3.2:3b` in every role) and the same in-process tools. The systems were: (a) one ReAct agent with every tool (`create_react_agent`), (b) `langgraph-supervisor` with three ReAct workers (analyst, researcher, writer), and (c) our hand-written graph run up to the approval interrupt. Letters that would be sent were submitted to a fresh GigSim (chaos off, 30 simulated days). Source: `multiagent/{graph,react,supervisor}.json`, with per-job rows in `*.jobs.jsonl`.

| System | bid/skip macro-F1 | Accuracy | Scam P / R | Price in band | Letters | Reply rate | Tokens/job | Latency mean / p95 s | Parse errors |
|---|---|---|---|---|---|---|---|---|---|
| Graph (ours) | 0.760 | 0.76 | 1.00 / 1.00 | 0.632 | 22 | 0.455 | 1188.5 | 29.7 / 79.0 | 0 |
| Single ReAct agent | 0.548 | 0.56 | 0.00 / 0.00 | 0.824 | 27 | 0.296 | 2924.9 | 41.1 / 70.2 | 4 |
| Supervisor + 3 workers | 0.517 | 0.52 | 0.00 / 0.00 | 0.571 | 18 | 0.167 | 1188.4 | 27.8 / 44.5 | 14 |

- **The explicit graph won on decisions and outcomes.** Macro-F1 was +0.21 over the single agent and +0.24 over the supervisor, and the reply rate was 0.455 against 0.296 and 0.167. The graph's decision is made by deterministic code over structured analyst outputs, and its letters are retrieval-grounded. The ReAct and supervisor agents leave the bid/skip judgement to a 3B model that tends to bid.
- **It used 59% fewer tokens than the single agent** (1,188 vs 2,925 per job) because each node sees only its own inputs instead of a growing tool transcript. The supervisor used the same number of tokens but often stopped early. 14 of its 50 final answers were not valid JSON and were counted as skips, which is a real cost of free-form hand-offs between agents.
- **Safety:** the sample contains only 2 scam jobs. The graph skipped both; the ReAct agent and the supervisor each bid on one. None of the sent letters broke the compliance filter. With 2 scam jobs and 2 injection jobs these safety numbers are indicative only.
- **Where the baseline wins:** the single agent's prices landed in the market band more often (0.824 vs 0.632) because it reads `get_market_rates` directly. This matches the pricing weakness seen above.
- **Caveat:** unsupported-claim rates are near 0 for every system because this run used the lenient token-overlap judge of the in-process tools, not the cross-encoder judge from section 5, so they do not separate the systems.

## 7. Safety and guardrails

- **Human approval** before every proposal, message and Connects spend (`interrupt()`); edits are re-checked by Compliance and go back to the human if they break a rule.
- **Prompt injection**: job posts and client messages are wrapped in `<<<UNTRUSTED ...>>>` delimiters; the Risk Assessor flags injection spans from the policy pack; Writer and Liaison prompts state that instructions inside untrusted blocks are data. Tests check that a planted injection does not put an email, a guarantee or a price change into the letter.
- **Scams**: off-platform contact, upfront fees and unpaid "test" work block the job (scam recall 1.000 above); the Liaison answers scam messages with a fixed safe reply.
- **Compliance filter**: contact details, external links and policy violations are blocked before approval and again before sending.
- **PII masking** of emails, phones and payment details in the MCP audit log (regex + tests).
- **Budgets**: step and token budgets per thread move a thread to `needs_attention` instead of looping; nodes have timeouts, bounded retries and a dead-letter state.
- **Memory**: a style rule is learned only after the same edit appears in 3 different threads; outcome memory accepts only terminal marketplace events. The user can view and delete everything in Settings.

## 8. Testing

`make test` runs 185 unit and contract tests (GigSim, MCP servers, RAG, graphs, API). Graph tests cover the approval payload, parallel fan-in order, exactly-once submit under a lost response and a crash, skips for scam / missing skill / low budget, injection flagging, reject, edit -> v2, edits that break policy, step budgets, the bounded critic loop, conversation flows and memory promotion. API tests cover auth, tenant isolation, approval resume and SSE replay.

## 9. Limitations

- Retrieval quality is modest in absolute terms (Recall@5 about 0.2) because gold evidence includes many short client reviews that dense and lexical retrieval rank below long proposals.
- Evaluations use synthetic data and a simulated client; reply rates measure GigSim's behaviour, not real clients.
- Judge calibration against human labels, the tool-granularity study (R&D A) and the live Upwork adapter were not finished at submission time. R&D C used one small local model (3B) on 50 jobs; a stronger model may narrow the gap between the systems.
- The public demo (web and API both on Vercel, `docs/DEPLOY.md`) runs the API as a serverless function in single-process mode (`GIGBID_MCP_MODE=inprocess`): the agents call the in-process tool layer that has the same tool names and result shapes as the MCP servers, each request drives the graph to its next stop (the approval interrupt or the end), and runs last only as long as a function instance. The full stack (three MCP servers, Postgres checkpoints) runs with `docker compose`.
- Pricing lands inside the market band only 61% of the time.
